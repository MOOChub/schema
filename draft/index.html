Abstract

The MOOChub metadata profile is a cross-sector metadata profile published under the MIT License license for the interoperable description of learning offers, courses, educational programmes, and related learning resources. The profile uses [[?JSON-LD 1.1]] and [[?JSON Schema Draft 2020-12]]. It is compatible with [[?AMB]] (the General Metadata Profile for Educational Resources) and extends it with more detailed information focused on courses, as well as profiles for educational programmes and credentials that can be earned. The domain concepts are drawn primarily from [[?schema.org]] and the AMB profile, supplemented by [[?SKOS]] concepts, European vocabularies for credential categories, and European semantics for learning outcomes from the European Learning Outcomes Vocabulary, together with MOOChub-specific constraints. The catalogue transport uses a paginated [[?JSON:API]] structure. A provider can offer different resource types that can be harvested independently in a shared feed, without translating the domain objects into a proprietary format.
This work is published under the MIT License.

Introduction

[[?MOOChub]] is a consortium of various MOOC portals, operators of online-learning platforms, higher education institutions, and higher-education associations. Its goal is to leverage synergies in online teaching and develop shared standards. MOOChub initially focused on the German-speaking higher education community and is now opening up to providers across Europe. Collaboration with international partners aims to make education accessible across institutional and national borders. MOOChub provides learners with a central point of access to MOOCs and other digital learning offers. This profile describes the machine-readable metadata that participating providers can use to exchange information about learning offers, courses, and educational programmes through open interfaces. The MOOChub profile is designed to remain compatible with AMB while providing more detailed information about learning offers and courses. It also describes educational programmes and credentials that can be earned. The profile focuses on a small, reliably exchangeable core: required information makes it possible to find and classify a course or programme, while optional information supports detailed search, presentation, and navigation to the offers. The profile additionally uses European vocabularies and semantics for credential categories and learning outcomes. The normative JSON Schemas are linked, for example, in the course schema, programme schema, and catalogue schema. Examples are part of the development process and illustrate typical valid and invalid documents.

Version status

This document describes the MOOChub v4 draft. The URLs used in the schemas therefore contain the `draft` path. Changes to required fields, value ranges, or JSON-LD semantics must be agreed upon before publication as a new version. Negotiation of parallel API versions and the sunset phase are described in API versioning.

API versioning

API versions MUST evolve in a backward-compatible manner. If a breaking change is required, the old and new versions MUST be offered in parallel for a transition period. The version applies to the API and transport format, not to the domain identity of a JSON-LD resource.

Version negotiation

Clients SHOULD specify the highest API major version they have implemented for each request. To do so, they set the moochub-version parameter in the Accept header. The parameter is used together with the JSON:API media type: 

GET /api/catalog HTTP/1.1
Host: provider.example
Accept: application/vnd.api+json; moochub-version=4

The provider MUST confirm the version actually served in the response's Content-Type header using the same parameter. If the request omits the version parameter, the provider may use the endpoint's latest supported version. A provider MUST either serve a requested version or reject it with 406 Not Acceptable; it MUST NOT silently serve an unsupported version as a different version. The response SHOULD include Vary: Accept. 

HTTP/1.1 200 OK
Content-Type: application/vnd.api+json; moochub-version=4
Vary: Accept

Sunset phase

During a sunset phase, providers MUST accept the previous and new API versions in parallel if both versions have been announced for the endpoint concerned. Every response MUST identify the version actually served. Clients MUST continue to request the version they support and MUST NOT infer a format change within a response from the existence of a new version.

For a deprecated version or one scheduled for decommissioning, the provider MUST include the HTTP Sunset header as specified in [[?RFC8594]]. Its value is an HTTP date indicating when the version concerned will no longer be supported:

HTTP/1.1 200 OK
Content-Type: application/vnd.api+json; moochub-version=3.8
Sunset: Tue, 15 Aug 2027 00:00:00 GMT
Vary: Accept

The sunset date MUST be communicated before decommissioning begins. Clients MUST monitor whether Sunset is present and its value, and plan their migration before that date. After the date has passed, the provider may reject the old version; such a rejection SHOULD use 410 Gone, or 406 Not Acceptable if the version is no longer available at the endpoint. The specific decommissioning MUST be announced to affected participants in advance.

Client behaviour

A client that supports both v3 and v4 MUST specify exactly the requested version for each request and check the confirmed version in Content-Type. A client that supports only v3 requests moochub-version=3 and treats a Sunset value as a migration signal. After a successful migration, it requests moochub-version=4 and checks again that the provider confirms this version.

Data format and JSON-LD

MOOChub objects are transmitted as JSON documents. The optional `@context` property can describe an object's JSON-LD meaning. It is not required in JSON:API attributes or embedded objects. A standalone JSON-LD document SHOULD include a compatible MOOChub context definition at the beginning of the document: 
{
  "@context": [
    "https://w3id.org/moochub/draft/context.jsonld",
    { "@language": "en" }
  ]
}
The language object sets the default language for localized values. Explicit language maps such as `{ "de": "...", "en": "..." }` remain permitted for localized plain-text fields. Language codes MUST be BCP 47-compatible. `id` is the JSON-LD identity and MUST be a URI. `url` denotes the publicly accessible presentation or offer page. These values are not necessarily identical.

Data model

The following sections define the object types in the MOOChub v4 profile. An object's JSON-LD type determines its object type, and properties can link it to other object types. For example, a course uses creator to refer to a Person or Organization object.

Course

A Course object describes a learning offer with a coherent subject. Its properties describe its identity, presentation, and domain content. Specific offerings that differ in time, location, or other respects are represented as CourseInstance objects through hasCourseInstance.

If a course's subject matter does not change significantly between semesters or offerings, it is recommended that these offerings be assigned to the same Course. If the content changes significantly, a separate Course may be more appropriate. The provider decides, based on its domain data, whether a new offering belongs to an existing course or represents a new course.

Skill Concept

A skill is described in MOOChub as a Concept. There is no additional dedicated data type for it.

Skill concepts SHOULD be included in a stable, published, and controlled vocabulary. Providers SHOULD use the original URIs, inScheme values, and labels from the relevant competency model. MOOChub particularly recommends the following models for skills:

JSON:API catalogue

The catalogue is a paginated JSON:API feed for independently harvestable Ressourcen wie `courses`, `programs`, `credentials`, `persons`, `organizations`, and `locations`. The transport structure is defined in api/catalogFeed.json definiert.

The catalogue MUST use the application/vnd.api+json media type and return a JSON:API 1.1 response. Resource types MAY be mixed in the same feed. Providers SHOULD offer a canonical catalogue endpoint and support filter[type], so harvesters can retrieve one or more homogeneous subsets when needed. Additional type-specific endpoints are permitted but MUST use the same identity space.

The catalogue uses a provider-local JSON:API ID in `data[].id`. The object's domain URI is in `data[].attributes.id`.

Pagination and filtering

The canonical query parameters are:

  • page[number]: one-based page number; the default is 1.
  • page[size]: requested page size. Providers MAY apply a documented maximum size and MUST indicate the actual page size through the links.
  • filter[type]: optional, comma-separated list of courses, programs, credentials, persons, organizations, and locations.

links.self is required. Providers SHOULD provide first, last, next, and prev. At the respective ends of the result set, next or prev is null. The order MUST remain stable throughout a complete harvesting run. meta.total MAY specify the total count after the filter has been applied.

A valid request, including one for an empty page, MUST return 200 OK. Invalid pagination or filter values MUST return a JSON:API error document with 400 Bad Request. Requests for non-existent resources SHOULD return 404 Not Found; 410 Gone MAY be used for resources that have been intentionally withdrawn.

Resource IDs and JSON-LD

data[].id is a non-empty, provider-local JSON:API ID. The domain JSON-LD resource in data[].attributes also has a stable URI in id. These identities serve different layers and do not need to have the same value.

Every independently harvestable object MUST have a stable attributes.id and a corresponding domain attributes.type. The combination of attributes.type and attributes.id forms the domain identity key. The JSON Schemas do not require an @context property. However, a standalone published JSON-LD document SHOULD include a compatible MOOChub context at the beginning of the document.

A compact reference object MAY contain only id, type, and optionally name. It denotes the same resource as a full representation and MUST NOT delete previously stored properties when merged.
